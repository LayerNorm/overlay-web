---
title: "On-Prem Backend Parity Program"
description: "The measurable program for reaching Convex and Postgres application parity before the JPIS AWS deployment."
---

This program turns "Postgres parity" from an architectural intention into a set of code-backed inventories, tests, and release gates. The target is not merely to run Overlay on Postgres. The target is to preserve the product behavior that users receive in Convex mode while removing Convex as a runtime dependency from the Postgres deployment.

The code source of truth is `src/server/app-data/parity-matrix.ts`. Generate the current report with:

```bash
npm run report:on-prem-parity
```

Do not infer parity from a provider name in the config schema. A domain is complete only when its matrix exit gate passes against both backends and the Postgres browser/server paths do not contact Convex.

## Program Boundaries

The work is split into two independently managed scopes.

### Product backend parity

This repository owns generic Overlay behavior that must work with both Convex and Postgres:

- Route behavior and response DTOs.
- Browser capability behavior.
- Repository and service contracts.
- Data lifecycle, authorization, cleanup, and audit behavior.
- Background work, retry, idempotency, and concurrency behavior.
- Deployment-independent integration, billing, and account behavior.

Parity work belongs in the shared application. It must not contain JPIS-specific table names, credentials, data-lake assumptions, or business rules.

### JPIS deployment customization

JPIS-specific work is a separate delivery stream built after or alongside the generic contracts:

- Proprietary data-lake connectors.
- Institution-specific context and retrieval policy.
- Student, staff, curriculum, and directory mappings.
- Customer-specific roles, workflows, administrative policy, and branding.
- AWS account, network, KMS, IAM, observability, backup, and disaster-recovery configuration.

These additions may consume Overlay extension points and domain services, but they do not count as Convex/Postgres parity. Keeping the scopes separate prevents a customer integration from becoming an accidental prerequisite for the main product and prevents generic application code from depending on one customer's systems.

## Tenancy Decision

JPIS uses one isolated deployment and one isolated app-data database for the pilot and initial production path. The deployment is the tenant boundary.

The isolation unit includes:

- One Overlay web/runtime deployment.
- One Postgres app-data database or isolated database/schema with dedicated credentials.
- One auth deployment/configuration.
- One object-store bucket or isolated namespace.
- One secret set, encryption-key set, log destination, and model-provider configuration.
- Dedicated background workers and queues when those phases are enabled.

Shared multi-tenant Postgres hosting is not part of the parity program. Runtime configuration continues to reject `capabilities.multiTenant=true`. Adding shared tenancy later requires tenant IDs, tenant-aware indexes, roles, keys, webhooks, storage namespaces, negative authorization tests, and migration/backfill design across every user-owned domain.

## Phase Map

| Phase | Scope | Required outcome |
| --- | --- | --- |
| P0 | Measurement, route inventory, runtime isolation, identity, app shell | Every capability and route family has one owner and exit gate. Direct Convex touchpoints cannot drift unnoticed. Postgres server/browser smoke can prove no Convex runtime traffic. |
| P1 | Production runtime foundations and model catalog | Shared idempotency, replay protection, distributed rate limits, leases, scheduler ownership, and restart-safe catalog behavior exist without Convex. |
| P2 | Chat | Send/read/title/stop/share/resume/reconnect and second-tab behavior match Convex, including durable stream recovery. |
| P3 | Projects | Project hierarchy, CRUD, associations, authorization, and UI behavior match Convex. |
| P4 | Files, notes, outputs, and generated media | Metadata, binary lifecycle, ingestion, sharing, duplicate handling, cleanup, generated outputs, retries, and DTOs match Convex. |
| P5 | Knowledge, memory, and vector search | Extraction, embeddings, `pgvector` retrieval, citations, reindex, retention, and deletion match Convex behavior. |
| P6 | Automations and webhooks | Durable scheduling, claims, retries, signed delivery, dead letters, and audit records work across worker replacement. |
| P7 | Integrations, extensions, skills, and MCP | OAuth/credential lifecycle, connector state, proxy/tool execution, scoping, discovery, and audit behavior match Convex. |
| P8 | Usage, billing, API keys, and enterprise controls | Usage reservations, budgets, Stripe replay safety, billing records, hashed keys, scopes, expiry, revocation, and audits match Convex. |
| P9 | Full release characterization and AWS rehearsal | All shared backend contracts and browser workflows pass on both providers, migration/recovery is rehearsed, and the AWS deployment has no unintended SaaS data-plane dependency. |

The phase assignment for each capability and route family is enforced by `ON_PREM_PARITY_MATRIX`. A capability or route rule cannot be added without being assigned to exactly one domain.

## P0 Controls

### Capability ownership

`src/server/app-data/parity-matrix.test.ts` compares the matrix with `AppDataCapabilities`. It fails when:

- A capability has no parity owner.
- A capability has multiple owners.
- An exit gate is blank.
- A target is not a boolean capability value.

`requiresConvexClient=false` is the parity target for Postgres. It is a successful isolation property, not a missing feature.

### Route inventory and characterization

`src/server/app-data/route-support.test.ts` discovers every exported HTTP method under `src/app/api/v1/**/route.ts`. It fails if a method has no Postgres route-support rule.

Each rule has one of these statuses:

- `supported`: intended to work in Postgres mode and must have behavior tests.
- `degraded`: intentionally reduced behavior with an explicit product contract.
- `unsupported`: capability-gated from the UI and rejected consistently by the server.

The parity matrix assigns every route-support rule to exactly one domain. Classification alone is not parity; later phases must move rules to `supported` and prove behavioral equivalence.

### Runtime and background-work baseline

`config/on-prem-convex-runtime-baseline.json` records:

- Every `src/app/api/**/route.ts` BFF route file, including non-v1 auth, billing, callback, and share routes.
- Files in `src`, `packages`, and `workers` that directly import, require, or dynamically import Convex runtime code.
- The browser subset of those direct Convex runtime touchpoints.
- Every registered job in `convex/crons.ts`, including cadence and target.
- Every Convex file that enqueues work through `ctx.scheduler.runAfter` or `ctx.scheduler.runAt`.

Tests, generated code, stories, and type-only imports are excluded from the runtime import inventory.

```bash
npm run check:on-prem-convex-boundaries
```

The check fails on additions and removals. Additions prevent accidental coupling. Removals are expected progress, but still require deliberate baseline review:

```bash
UPDATE_ON_PREM_CONVEX_BASELINE=1 npm run check:on-prem-convex-boundaries
git diff -- config/on-prem-convex-runtime-baseline.json
```

The complete route list is frozen here while `/api/v1` methods receive the stricter support classification described above. This is an inventory guard, not a complete data-flow proof. Indirect network traffic is covered by runtime smoke tests.

### No-Convex server smoke

```bash
npm run test:on-prem:no-convex-server
```

The test removes Convex environment variables, traps network access, constructs a Postgres server context, verifies Postgres repositories and local/no-op policies, and exercises safe rate-limit and usage-policy methods. It proves bootstrap does not require Convex configuration or network access. Real repository behavior remains covered by Docker Postgres contract tests.

### No-Convex authenticated browser smoke

The browser smoke checks the session, verifies the server reports `provider=postgres` and `requiresConvexClient=false`, visits supported app surfaces, and fails on Convex HTTP or WebSocket traffic.

First capture an authenticated state against the deployment under test. The `.auth` directory is gitignored.

```bash
mkdir -p .auth
npx playwright codegen \
  --channel=chrome \
  --save-storage=.auth/on-prem.json \
  https://overlay-onprem.example.com/app/chat
```

Complete sign-in in the opened browser, confirm `/app/chat` loads, then close the codegen window. Run:

```bash
ON_PREM_SMOKE_URL=https://overlay-onprem.example.com \
ON_PREM_SMOKE_STORAGE_STATE=.auth/on-prem.json \
npm run test:on-prem:no-convex-browser
```

The default route set is `/app/chat,/app/files,/app/settings`. Override it with `ON_PREM_SMOKE_PATHS`. A signed-out-only check is available with `ON_PREM_SMOKE_EXPECT_AUTHENTICATED=0`, but it is not sufficient for a parity release gate.

### Real backend contracts

Repository contracts remain mandatory:

```bash
npm run test:app-data-contracts:postgres
npm run test:app-data-contracts:convex
```

Docker is only one way to provide the Postgres fixture. For a dedicated remote
test database, create the gitignored `.env.on-prem-contract-tests.local` with
`OVERLAY_DATABASE_URL` set to a direct, unpooled connection and run:

```bash
npm run test:app-data-contracts:postgres:remote
```

Use a database reserved for contracts. The P1 suite resets scheduler-owned
tables and must never target staging or production app data.

The same behavioral contract must run against both implementations. As each later phase adds a repository or service invariant, it must add that behavior to the shared suite rather than creating unrelated provider-only expectations.

## P0 Exit Gate

P0 is complete when all of the following are true:

- The work is on the dedicated `codex/on-prem-parity` branch/worktree.
- Every app-data capability belongs to exactly one parity domain.
- Every `/api/v1` exported method is classified for Postgres.
- Every BFF route, browser Convex runtime touchpoint, Convex cron, and scheduler enqueue file is inventoried.
- Every Postgres route-support rule belongs to exactly one parity domain.
- The direct Convex runtime inventory is checked into source control and cannot drift silently.
- The no-Convex server smoke passes without Convex env vars.
- The authenticated browser smoke exists as a repeatable deployment gate and passes on each Postgres staging/AWS environment before promotion.
- JPIS custom integration scope is documented separately from generic parity.
- JPIS tenancy is one isolated deployment/database; shared multi-tenancy remains disabled.
- The matrix report and all P0 checks can be run from package scripts.

Run the local P0 gate with:

```bash
npm run check:on-prem-parity
npm run report:on-prem-parity
```

P0 does not claim full backend parity. It makes the remaining work measurable and prevents the application from acquiring new untracked Convex dependencies while that work proceeds.

## P1 Production Runtime Foundations

P1 replaces process-local or Convex-only coordination in the Postgres runtime with shared infrastructure:

- API idempotency reservations and replay responses are stored in Postgres and are atomic across app instances.
- Internal service-auth replay nonces are consumed once through the selected app-data repository.
- Redis rate limits use an atomic increment/expiry operation. Production and on-prem Redis configurations fail closed when Redis is unavailable; memory fallback is development-only.
- Durable jobs and outbox events use Postgres claims, leases, heartbeats, retries, and dead-letter states.
- The Postgres scheduler uses row locks and deterministic dedupe keys so competing scheduler replicas enqueue one execution.
- Model-catalog snapshots are persisted through the selected app-data repository and remain available after app restarts.
- App-data migrations take a Postgres advisory lock and write explicit schema compatibility metadata. The Node runtime refuses to start against an incompatible schema.

The generic durable runtime is intentionally separate from domain parity. P1 provides the execution substrate, but automations and webhook product behavior remain disabled until P6 adds their handlers, audit records, and shared behavioral tests.

Run the P1 gate with Docker Postgres and Redis:

```bash
npm run check:p1
npm run app-db:worker:smoke
```

The Postgres portion can run without Docker against the dedicated remote test
database:

```bash
npm run test:p1:unit
npm run test:p1:postgres:remote
```

The real Redis integration still requires a disposable Redis endpoint.

For a deployed Postgres runtime, run migrations as a one-off release task, then run at least one long-lived worker/scheduler process:

```bash
npm run app-db:migrate
npm run app-db:worker
```

The worker must not be embedded only in an autoscaled web process. Deploy it as a separately supervised ECS service, Kubernetes Deployment, systemd service, or equivalent. Multiple replicas are supported; leases and `SKIP LOCKED` claims prevent duplicate ownership.

### P1 Exit Gate

P1 is complete when:

- Migration locking and schema compatibility tests pass against real Postgres.
- Two repository instances prove atomic API idempotency and replay nonce consumption.
- Two workers cannot claim the same job or outbox event.
- Expired leases are recovered and exhausted work reaches dead-letter state.
- Competing scheduler instances enqueue one job for each due schedule.
- Redis counters are shared across limiter instances and production failure mode is fail-closed.
- A persisted model-catalog snapshot survives repository replacement.
- `npm run app-db:worker:smoke` completes a real durable health-check job.

P1 does not claim project, vector, automation, webhook, integration, billing, or API-key parity. Those remain owned by P2-P8.

## P2 Chat Realtime And Recovery

P2 makes persisted chat behavior independent of Convex:

- Conversation and message mutations use `ActConversationRepository` for both providers.
- Postgres writes a per-user `conversation_events` record in the same transaction as each chat state change.
- Browser tabs long-poll `/api/v1/conversations/events` with a durable sequence cursor. Transactional `pg_notify` wakes one shared listener per app process, while a reconnect resumes from the table after the last observed sequence instead of relying on notifications or process memory.
- Text deltas are batched into Postgres while the model streams. The server keeps a background stream consumer alive after a browser disconnect, so the aggregate message can continue to advance.
- Refresh and second-tab recovery reload the authoritative persisted message snapshot. Local active streams are not overwritten by their own event notifications.
- Stop locks generating rows, persists the interruption sentinel, deletes obsolete deltas, and prevents a late model completion from overwriting the stopped result. Other tabs stop their local reader when they observe the event.
- Conversation share visibility, public-token reads, turn deletion, generated UI updates, and stream relay ownership checks all use the selected repository.
- The optional chat-stream relay can still replay exact UI stream frames. Postgres recovery does not require that relay: without it, recovery resumes from the latest durable text/message snapshot.

Knowledge suggestions, notebook-agent behavior, and extension planning are not P2 chat dependencies. They remain capability-gated and are owned by P5 and P7.

Run the P2 gate with Docker Postgres:

```bash
npm run check:p2
```

Or run the database-independent and real-Postgres portions without Docker:

```bash
npm run test:p2:unit
npm run test:p2:postgres:remote
npm run check:on-prem-parity
```

### P2 Exit Gate

P2 is complete when:

- Postgres capabilities report realtime, stream recovery, and chat persistence.
- Every core conversation route is classified as supported.
- Real Postgres contracts cover ordered event cursors, message deltas, stop/finalize races, sharing, turn deletion, and account cleanup.
- Refresh during generation recovers the latest persisted text and eventually the final response.
- A second tab receives list, title, message, stop, and completion changes without mounting Convex.
- Public share links load through the selected app-data repository.
