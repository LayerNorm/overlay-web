[Development Workflow](https://github.com/LayerNorm/overlay-web/blob/main/docs/develop/Development%20Workflow.md) is authoritative: main changes deploy directly to Vercel production, then production smoke. Staging is optional. This guide covers supporting deployment and optional hosted QA details only. Follow [Agentic Development](/develop/agentic-development) for feature branches, worktree creation, pull requests, commit history, and integration ownership.

## Native production deployment

Vercel’s native Git integration deploys main from LayerNorm/overlay-web to
Divyansh’s overlay-landing project. Git is enabled as a production source,
main is the production branch, and automatic production domain assignment is on.
Keep root git.deploymentEnabled.main=true. The custom Production Release workflow,
promotion script and Vercel production deployment token are retired.

After merge, verify Vercel's deployment SHA and the live production domain.
Integration runs proportionate authenticated production smoke. For backend changes,
synchronize colorful-chickadee-419 only from clean current canonical main after
matching web is live, using its private production-scoped Convex key. Do not push
Convex for frontend-only releases. Never pass .env.local to production or seed
customer production. See [Convex Workflow](/develop/convex-workflow).

Use the synthetic production QA account for sign-in, note CRUD/conflict/cleanup,
chat reply and reload persistence, Files and realtime checks when relevant.
Use normal browser/application QA for native Git deployments. The older production
smoke helper expects custom promotion metadata and is retained only for historical
release evidence; do not use it to certify a native Git deployment.
A Git deployment alone does not prove backend synchronization or application QA.

### Rollback runbook

1. Inspect the saved production checkpoint and verify the previous deployment
   belongs to `overlay-landing`, its revision and compatibility with the current
   backend. Use `vercel inspect <deployment-id> --format json` with the verified
   Divyansh scope. Keep that exact previous web ID in the release evidence.
2. With rollback authorization, run `vercel rollback <verified-deployment-id>
   --yes --scope divyansh-lalwanis-projects`. Verify the production project,
   canonical alias and authenticated application behavior afterward. Record the
   actual returned deployment/alias IDs; an attempted CLI call is not proof.
3. Retain the current backward-compatible Convex functions for the immediate
   web rollback. If functions must also be restored, review a revert on `main`
   that restores the previous function source while preserving expanded schema
   and customer data. Use optional staging if explicitly requested, then deploy its web first
   and push its production functions from clean canonical `main`. Never use a
   feature checkout, force/reset `main`, or deploy an obsolete schema over data
   written since release. Record the previous-source revision and any retained
   compatibility fields.
4. The migration completed a deliberate live web rollback, authenticated compatibility smoke, restoration and full current-release smoke. Each later rollback still requires owned deployment/alias readback and relevant behavior checks.

## Deployment lanes

| Lane | Source | Web | Convex |
| --- | --- | --- | --- |
| Preview | Internal main PR head | `pr-<number>.preview.getoverlay.io` | Per-PR preview, synthetic sandbox fixtures |
| Staging | Accepted main SHA | `staging.getoverlay.io` | `doting-cuttlefish-819`, dedicated sandbox/test providers |
| Customer production | Automatically promoted current main SHA | `getoverlay.io` | `colorful-chickadee-419`, production identity/providers |

The legacy staging branch is frozen. There is no staging-to-main release PR or
branch-parity work. Local development uses an engineer-owned development backend.

### Preview lifecycle

Trusted main control creates ordinary custom aliases, verifies current PR head
before assignment, and keeps model/storage/test secrets inherited from shared
Preview web and Convex defaults. Native Git previews stay disabled; controller
API builds require canonical origin and scoped preview key. Docs/root-Markdown/
GitHub-only diffs skip hosted app builds while retaining required checks.
`needs-preview` or manual dispatch requests one. Unknown/app/build/dependency
changes build. Closing/merging removes owned aliases, domain and URL overrides;
reconciliation every six hours repairs missed events and renews open backends.
Closed/unknown preview hosts return HTTPS 404. Backend retention is a platform
limit, independent of the non-expiring shared credentials.

### On-demand release candidate

Dispatch `staging-release.yml` manually only for explicitly requested sensitive-change acceptance. The candidate workflow itself has no push trigger. All candidates share one serialized lock. The staging project's Production
branch is main; Production and Preview deployment sources permit controller REST
API builds only. The staging project’s native Git deployments remain disabled; root main Git deployment is enabled for customer production. The ignore/build
guards accept an exact trusted-main SHA override and reject unrelated refs,
manual builds and wrong backends. Automatic custom-domain assignment is disabled.

The remote build deploys dedicated staging functions, invokes guarded synthetic
seed, then builds web with the same backend URL. Controller verifies repository,
main SHA, project, backend and READY state before alias assignment. The same job
runs Sandbox sign-in, fixture reads, note CRUD/stale-edit conflict/cleanup, a real
chat reply, Files UI and realtime own-user/other-user authorization. Inspect
`Staging Deploy`, `Staging Smoke`, artifacts and screenshots for that exact SHA.
A ready web build or stale smoke result is insufficient for production.

Every dispatch keeps the canonical alias unchanged while testing the verified
native candidate hostname.
After isolated provider proof, `STAGING_ISOLATION_VERIFIED=enabled` plus
`publish_candidate=true` permits same-run publication only after smoke passes.
Canonical smoke runs again if publication is requested. A successful unpublished
candidate also qualifies for promotion: an explicitly staging-gated command verifies its native origin,
ready deployment provenance, successful trusted manual producer and current main.
The persistent staging project/backend are reused for these checks and PR previews;
there is no staging branch workflow. Ordinary automatic production releases do not use this candidate.

```bash
gh run list --repo LayerNorm/overlay-web --workflow staging-release.yml
gh run view <run-id> --repo LayerNorm/overlay-web
```

For explicitly requested staging acceptance, verify current origin/main equals the
smoke SHA and the candidate origin (or optional canonical staging alias) serves
that exact deployment. If main advances or smoke fails, verify the new revision.
This optional evidence does not gate ordinary native Vercel production deployment.

## Integration checklist

1. Review exact PR head, resolved findings, required checks and affected preview QA.
2. Enqueue through main's merge queue; verify accepted main SHA after merge.
3. Verify Vercel’s native production deployment, synchronize Convex only for backend changes, then run production smoke.
4. Use `needs-staging` only for explicitly requested sensitive-change acceptance.
5. Verify the automatic guarded promotion used clean current main and published web before production Convex.
   Manual recovery requires authorization and the same promotion command.
6. Preserve checkpoints and previous deployment IDs; run authenticated QA and
   verify any rollback through actual alias readback. Report incomplete work clearly.

### Production deployment ownership

Native Vercel Git owns web builds and publication. Integration checks the actual
live revision and affected behavior. No GitHub production deploy job or deployment
token is needed. Optional staging remains manually dispatched and separate.

Closed preview backends can temporarily exhaust the team deployment quota before
retention expires. Audit exact project/type/PR ownership and closed PR state before
removing obsolete synthetic previews. Keep open previews and shared deployments.
