## Production promotion command

`bash scripts/release/promote.sh <40-character-main-sha> --check` performs
preflight only. Omitting `--check` manually releases that exact current `main`.
The command requires a successful on-demand release candidate for current main.
Production Release dispatches this candidate automatically after main changes.
Canonical staging alias publication remains optional.

Run it from clean canonical `main`, linked to Divyansh's production project.
Provide `CONVEX_PRODUCTION_DEPLOY_KEY` scoped to `colorful-chickadee-419`, and
`PRODUCTION_SMOKE_EMAIL`, `PRODUCTION_SMOKE_PASSWORD`, `PRODUCTION_SMOKE_USER_ID`
for the separate `overlay-release-qa@getoverlay.io` synthetic production account.
The account must have a personal workspace; do not use the sandbox QA user or a
customer account. The production QA identity is now provisioned separately in
the production WorkOS environment. Identity readback and direct WorkOS password
authentication, application sign-in and the complete live production smoke passed on the accepted release. Subsequent revisions require fresh proof.
Its password and the deployment-scoped Convex key (expires 2027-01-10) are stored
privately on the owner's machine, outside the checkout and preview configuration.
The command loads those four settings from
`~/.config/overlay/release/production.json` after validating canonical main.
The prepared file uses mode `0600` in a private directory. Set
`OVERLAY_PRODUCTION_RELEASE_CONFIG` to use another private JSON file, or supply
the four environment variables explicitly. Unknown JSON fields are ignored;
explicit environment values take precedence. This file is never part of a web
deployment upload and does not replace production provider settings on Vercel.
The native
GitHub/Vercel CLI accounts must be `DevelopedByDev`/`developedbydev1`. Install the
reviewed dependencies and Playwright Chromium before release.

The command downloads the successful manually dispatched candidate workflow's
exact smoke artifact, checks all ten behavioral checks and its producer, and
verifies its native origin and ready deployment provenance (or published alias). Older proof without realtime authorization
does not qualify. It then remotely builds production web without assigning
domains, checks provenance, publishes and verifies the canonical web alias,
pushes production Convex using a private key-only env file, and performs normal
sign-in, note CRUD/conflict/cleanup, persisted chat, Files and realtime QA.
Files checks target the accessible named file button; scope the locator to the
main Files region when the sidebar exposes a button with the same name.
The chat composer is the accessible `Ask anything` combobox, not a textarea.
No production seed runs. Root `git.deploymentEnabled.main=false` prevents a
duplicate native Git deployment bypassing the automatic release gates.

The production Convex target is announced before its push. Neither `.env.local`
nor conflicting development selectors authorize that push. Failure stops later
steps; checkpoints and screenshots are saved under ignored
`artifacts/release-workflow/promotions/`. A local Git-directory lock prevents
simultaneous invocations in this checkout. A failed command may have already
published web or backend: read `lastCompletedState` and the previous deployment ID.

1. Inspect the saved production checkpoint and verify the previous deployment
   belongs to `overlay-landing`, its revision and compatibility with the current

2. With rollback authorization, run `vercel rollback <verified-deployment-id>
   --yes --scope divyansh-lalwanis-projects`. Verify the production project,
   canonical alias and authenticated application behavior afterward. Record the
   actual returned deployment/alias IDs; an attempted CLI call is not proof.
3. Retain the current backward-compatible Convex functions for the immediate
   web rollback. If functions must also be restored, review a revert on `main`

   and customer data. Test that revision on staging, then promote its web first
   and push its production functions from clean canonical `main`. Never use a
   feature checkout, force/reset `main`, or deploy an obsolete schema over data
   written since release. Record the previous-source revision and any retained
   compatibility fields.
4. The migration completed a deliberate live web rollback, authenticated compatibility smoke, restoration and full current-release smoke. Each later rollback still requires owned deployment/alias readback and relevant behavior checks.

### Preview lifecycle

Trusted main control creates ordinary custom aliases, verifies current PR head
before assignment, and keeps model/storage/test secrets inherited from shared
Preview web and Convex defaults. Native Git previews stay disabled; controller
API builds require canonical origin and scoped preview key. Docs/root-Markdown/
GitHub-only diffs skip hosted app builds while retaining required checks.
`needs-preview` or manual dispatch requests one. Unknown/app/build/dependency
changes build. Closing/merging removes owned aliases, domain and URL overrides;
reconciliation every six hours repairs missed events and renews open backends.
Closed/unknown preview hosts return HTTPS 404. Backend retention is a platform
limit, independent of the non-expiring shared credentials.

### On-demand release candidate

Production Release dispatches `staging-release.yml` after main pushes. Manual
staging-only dispatch remains available. The candidate workflow itself has no push trigger. All candidates share one serialized lock. The staging project's Production
branch is main; Production and Preview deployment sources permit controller REST
API builds only. Root Git main deployments remain disabled. The ignore/build
guards accept an exact trusted-main SHA override and reject unrelated refs,
manual builds and wrong backends. Automatic custom-domain assignment is disabled.

The remote build deploys dedicated staging functions, invokes guarded synthetic
seed, then builds web with the same backend URL. Controller verifies repository,
main SHA, project, backend and READY state before alias assignment. The same job
runs Sandbox sign-in, fixture reads, note CRUD/stale-edit conflict/cleanup, a real
chat reply, Files UI and realtime own-user/other-user authorization. Inspect
`Staging Deploy`, `Staging Smoke`, artifacts and screenshots for that exact SHA.
A ready web build or stale smoke result is insufficient for production.

Every dispatch keeps the canonical alias unchanged while testing the verified
native candidate hostname.
After isolated provider proof, `STAGING_ISOLATION_VERIFIED=enabled` plus
`publish_candidate=true` permits same-run publication only after smoke passes.
Canonical smoke runs again if publication is requested. A successful unpublished
candidate also qualifies for promotion: the command verifies its native origin,
ready deployment provenance, successful trusted manual producer and current main.
The persistent staging project/backend are reused for these checks and PR previews;
there is no staging branch workflow. Automatic releases test a fresh candidate after each main push.

```bash
gh run list --repo LayerNorm/overlay-web --workflow staging-release.yml
gh run view <run-id> --repo LayerNorm/overlay-web
```

Before promotion, verify current origin/main still equals the smoke SHA, its verified native origin (or optionally published
canonical alias) serves its deployment and all required behavioral checks passed.
The production command checks this automatically. If main advances or smoke
fails, wait for and verify the new revision; do not promote older proof.

### Automatic production after main changes

The owner enabled automatic releases on 2026-10-14. `production-release.yml` runs
on every main push and supports manual retry on main. Its non-canceling production
concurrency lock covers candidate dispatch, acceptance and promotion. It dispatches
the existing Release Candidate workflow and accepts only a new successful run for
the exact SHA. If main advances, publication stops; the latest queued release
handles the new main. Failed candidate acceptance leaves customer production alone.

The `production-release` GitHub environment permits only main. Its secrets are the
existing production Vercel token, exact production Convex key, and three synthetic
production smoke settings. Dependency installation receives none of these secrets.
GitHub uses the ephemeral Actions token; the promotion command verifies its active
main workflow run instead of requiring a personal GitHub token. Web is built remotely,
published and verified before customer Convex changes; authenticated smoke follows.
Evidence is uploaded as `production-release-<sha>`, including previous deployment
IDs and the last completed phase. A failed post-publication step may leave web or
backend live: inspect the checkpoint before retrying or authorizing rollback.

`git.deploymentEnabled.main=false` remains intentional: the Actions workflow
automatically deploys to Vercel; native Git builds would bypass candidate acceptance
and race the production backend. No paid preview suffix or staging branch is used.
Disable the Production Release workflow to pause automatic releases.
