Treat each web deployment and its Convex deployment as one release unit. Push the development deployment from the dedicated `staging` worktree for staging QA, then push production from the clean `main` worktree after the matching web deployment is live:

```bash
# staging worktree only
npm run convex:push:dev

# clean main worktree only
npm run convex:push:prod
```

| Lane | Web | Convex deploy command | Convex URL env on that web project |
| --- | --- | --- | --- |
| Shared staging | `staging.getoverlay.io` | `npm run convex:push:dev` from `overlay-landing-staging` | `NEXT_PUBLIC_CONVEX_URL` → development deployment |
| Production | `www.getoverlay.io` | `npm run convex:push:prod` from clean `main` | `NEXT_PUBLIC_CONVEX_URL` → production deployment |

Staging chat failures after a branch merge are usually env pairing, not missing
git history: wrong or doubled Convex URL, `INTERNAL_API_SECRET` mismatch, or a
missing `convex:push:dev` after `convex/` changed. See
[Worktree Staging QA](/develop/worktree-staging-qa#pair-staging-web-with-development-convex).

Do not use `convex:push:all` in a worktree workflow. Never pass `.env.local` to a production Convex deploy; use the dedicated production script instead.
