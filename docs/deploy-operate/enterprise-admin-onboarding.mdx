This guide is for the first administrator of an enterprise or managed-cloud Overlay deployment.

## First admin

The first admin is normally granted by the deployment operator or by the [One-Command Install](./one-command-install) bootstrap script. If you need to grant it manually, use the admin helper:

```bash
OVERLAY_DATABASE_URL='postgresql://overlay_app:password@database.example.com:5432/overlay_app' \
OVERLAY_DATABASE_SSL_MODE=verify-full \
npm run app-db:admin -- grant \
  --user-id user_123 \
  --role admin \
  --reason "Initial enterprise admin"
```

This creates an `administrative_principal` record and records the grant in the audit log.
Run the command from the checked-out release with the application database
role. Do not use the Better Auth database URL or an RDS administrator role.

## Grant and revoke principals

Admins can list, grant, and revoke administrative principals through the admin API.

```bash
GET /api/v1/admin/principals
POST /api/v1/admin/principals
DELETE /api/v1/admin/principals
```

Request bodies:

```json
// Grant
{
  "userId": "user_123",
  "role": "admin",
  "reason": "IT administrator"
}

// Revoke
{
  "userId": "user_123"
}
```

Valid roles are `admin`, `auditor`, `billing_admin`, and `support`.

## Roll out capability enforcement

Overlay creates immutable system roles for administrative compatibility and a
`[System] Default member` role for ordinary product access. New users receive
the default role after their identity is persisted. Existing users must be
migrated before switching enforcement on:

```bash
NODE_OPTIONS=--conditions=react-server \
npx tsx scripts/migrate-administrative-authorization.ts
```

The command reports how many existing users received a baseline assignment.
Run it once against each deployment database. It is idempotent.

Start a deployment in observation mode:

```bash
OVERLAY_AUTHORIZATION_ENFORCEMENT_MODE=observe
```

In observation mode, Overlay evaluates and logs missing capabilities without
blocking requests or hiding UI. Review the logs, create any custom roles and
groups, assign them, and revoke the default Member assignment from users who
must be restricted. A user with any explicit role is not automatically given
the default role again. An empty custom role can therefore represent a
suspended account.

After the observation window is clean, switch every web, worker, and scheduler
process together:

```bash
OVERLAY_AUTHORIZATION_ENFORCEMENT_MODE=enforce
```

Denied mutations create redacted `authorization.request.denied` audit events.
API-key scopes remain an additional restriction: a valid key must have both the
required API-key scope and the owning user's effective Overlay capability.

## Read audit events

Auditors and admins can list audit events:

```bash
GET /api/v1/admin/audit?limit=20
```

Use `action`, `actorUserId`, `resourceType`, and `before` filters to narrow results.

## Manage budgets

Admins and `billing_admin` can read usage and adjust budgets:

```bash
GET /api/v1/admin/usage?userId=user_123

POST /api/v1/admin/usage
{
  "userId": "user_123",
  "amountCents": 5000
}
```

Budget adjustments create `administration.budget.adjust` audit events.

## Checklist

Before handing the deployment to end users:

- [ ] The first admin is granted and has signed in.
- [ ] Additional admin roles are granted and documented.
- [ ] Existing users were migrated to the default Member role.
- [ ] Custom restricted roles were tested in observation mode.
- [ ] Web, worker, and scheduler processes use the same enforcement mode.
- [ ] Audit logging is enabled and reachable.
- [ ] Usage and budget controls are understood by the finance/IT contact.
- [ ] The [Enterprise Security Launch Checklist](./enterprise-security-launch-checklist) is complete.
